## 一、Elasticsearch 搜索（事务后置双写 + 重试补偿 + 降级）

### 1. 一分钟口语版（背这段）

> 这个项目里有大量"按名称模糊搜"的场景，比如搜合约条款、供应商。原来走 MySQL 的 like '%关键词%'，有两个问题：一是前缀带 % 索引直接失效，只能全表扫描，数据涨上来之后越来越慢；二是 like 只能匹配字面，搜"螺纹钢保证金"就搜不到正文里写"螺纹钢的保证金比例"的记录。
>
> 所以我引入了 ES 7.16 加 IK 中文分词。IK 把中文按词切开后建倒排索引，任意位置的词都能命中，不用扫全表。实测搜索从秒级降到了 2 到 28 毫秒。
>
> 引入 ES 最大的难点是**数据一致性**。MySQL 是数据源，ES 只是加速层，两边数据必须一致。我用的是"事务后置双写"：业务在 MySQL 的事务里正常写，事务**真正提交之后**，再通过 Spring 的 afterCommit 回调把数据推到 ES。为什么不放在事务里写？因为事务可能回滚——MySQL 回滚了但 ES 已经写进去，就出现"ES 有、库里没有"的脏数据。
>
> 双写失败了怎么办？ES 挂了不能把主业务拖死。所以任何写 ES 的异常都被捕获，落一张 es_retry_task 重试表；后台有个定时任务每分钟扫这张表做补偿。补偿时有个细节：不是把当年失败的旧文档重放进去，而是**回头查 MySQL 拿最新数据**重建文档——因为失败期间数据可能又改过了；如果查出来 MySQL 里这条已经删了，就把 ES 里的也删掉，实现自愈。重试超过上限标 DEAD 等人工处理。
>
> 最后是降级：搜索接口调 ES 抛异常时，不返回 500，而是返回 success=false 加一个明确提示，前端据此回退到原来的数据库分页接口。整个链路里 ES 挂掉只影响"搜得快不快"，不影响"能不能用"。

### 3. 追问应答

- **Q：为什么不用 Canal 监听 binlog 做同步？**
  A：Canal 是独立部署的中间件，要维护 binlog 位点和消费程序，适合多系统订阅的场景。我们是单体应用，双写加补偿表在自己的事务边界内就能解决，成本低、链路短、排查直接。如果以后拆微服务、多个下游都要感知数据变更，再上 Canal 或 MQ 广播。
- **Q：afterCommit 里写 ES，进程刚好在这时候挂了呢？**
  A：这个窗口确实存在，兜底就是重试表 + 我另外写了全量同步接口，极端情况可以全量重建索引。这是"最终一致"的取舍，不是强一致。
- **Q：为什么搜索这么快？**
  A：like '%x%' 是全表扫描；ES 是倒排索引，先分词、按词建"词→文档列表"的映射，查的时候直接查表拿文档 id，复杂度和数据量近似脱钩。
- **Q：ES 和 MySQL 谁是主数据？**
  A：MySQL。ES 文档丢了可以从 MySQL 全量重建（项目里有 `/api/es/sync/full` 接口）；反过来不行。所有 ES 写入口都套在 try-catch 里，它挂了业务照常。

## 二、MyBatis-Plus 持久层

### 1. 一分钟口语版

> 持久层我按"单表"和"多表"分两种打法。
>
> **单表**全部走 MyBatis-Plus 的 BaseMapper：增删改查、按条件查，直接继承接口就有，不用写 SQL；条件用 LambdaQueryWrapper 构造，比如查"合约代码等于 RB2410"，写 `Wrappers.lambdaQuery().eq(FuturesContract::getContractCode, code)`——用方法引用写字段名，编译期就能查错，重构改字段名时 IDE 能跟着改，不会出现字符串写错到运行时才炸。
>
> **分页**是 IPage 加分页插件：Mapper 方法第一个参数放 IPage 对象，插件（PaginationInnerInterceptor）会自动拦截 SQL 拼上 limit 和 count，返回的对象里直接带总条数和当前页数据，不用自己写两条 SQL。
>
> **多表关联**不走 Wrapper，手写注解 SQL：`@Select` 直接写 join，字段映射用 `@Results`/`@One` 配，比如查合约时分页、按品种名过滤、按合约代码模糊搜，就是一条 `join trading_variety` 加动态 like 的 SQL。另外给 ES 做数据同步时，因为 ES 文档要冗余品种名、交易所名这些"别的表的名字"，我还写了几条三表、四表的 left join 聚合查询。

### 2. 源码对照

| 讲的点 | 文件 | 关键代码 |
|-------|------|---------|
| 分页插件 | `configure/MybatisPlusConfig.java` | `MybatisPlusInterceptor` + `PaginationInnerInterceptor` |
| 注解 SQL 两表 join + 模糊查询 | `dao/FuturesContractMapper.java` | `findAllByPage()`：`@Select("...join trading_variety tv on ... and (#{keyWord} is null ... or fc.contract_code like concat('%',#{keyWord},'%') ...")`，第一个参数 `IPage` 自动分页 |
| 关联对象映射 | 同上 | `@Result(column="variety_id", property="tradingVariety", one=@One(select="...findById"))` 嵌套查关联的品种对象 |
| Lambda 条件构造器 | `ai/tool/impl/ContractImportTools.java` | `selectOne(Wrappers.lambdaQuery().eq(FuturesContract::getContractCode, ...).last("limit 1"))` |
| 主键回填 | `dao/FuturesContractMapper.java` | `@Options(useGeneratedKeys=true, keyProperty="contractId")` 插入后拿自增 id |
| 三表/四表 left join | `es/sync/EsFullSyncService.java` | `futures_contract_text t left join trading_variety v ... left join exchange e ... left join industry i ...` 一次把 ES 文档要的名字字段都补齐 |
| 实体与表映射 | `pojo/FuturesContract.java` | 表字段驼峰自动映射；非表字段标 `@TableField(exist=false)`（联表对象必须标，否则 MP 会把它当列名拼进 SQL，报 Unknown column——这是我踩过的真实坑） |

### 3. 追问应答

- **Q：Wrapper 和注解 SQL 怎么选？**
  A：单表、条件动态拼 → Wrapper，类型安全还少写 SQL；多表 join、复杂聚合 → 手写 SQL 更直观可控。项目里两条腿都有。
- **Q：分页插件原理知道吗？**
  A：MyBatis 拦截器（Interceptor）机制，拦截 StatementHandler，改写 SQL 追加 limit，并额外发一条 count 查询算总数。
- **Q：`@TableField(exist=false)` 是干嘛的？**
  A：实体里有联表对象（比如合约实体里的 tradingVariety），它不是本表列。不标注的话 MyBatis-Plus 生成 SQL 会带上这个属性对应的列名，数据库里没有这列就报 Unknown column。我踩过一次：老代码全走自定义 @Select 没暴露，后来 AI 工具走了 BaseMapper 的查询才炸出来。

## 三、AOP 操作日志 ✅【2026-09-23 已补齐，`verify-operlog.sh` 14/14 通过】

> 💡 **代码看不懂的话，先看 `docs/操作日志-逐行白话讲解.md`** —— 逐行白话解释 + 照着念的话术 + 追问应答。
> 本节是精简版，那边是逐行版。

### 1. 一分钟口语版（背这段）

> 我用 Spring AOP 做了操作日志。自定义一个 @OperLog 注解，写模块名和动作名，加在 Controller 方法上就行——业务代码里一行日志都不用写，以前那种每个方法里手写"取时间、try-catch、落库"的样板代码全删掉了。
>
> 切面用 **@Around 环绕通知**，这个选择是有原因的：耗时、正常返回、抛异常三种状态要在一个地方算完。如果用 @Before + @AfterReturning + @AfterThrowing 三个通知，开始时间只能存成员变量，而切面是单例，并发下 A 请求的开始时间会被 B 请求覆盖，耗时全乱。环绕通知用方法内的局部变量，天然线程安全。
>
> 记录的内容是：模块、动作、目标方法、请求参数、客户端 IP、耗时、成功还是失败。IP 那里有个坑——不能只用 getRemoteAddr，应用一旦挂在 Nginx 后面，拿到的是代理服务器的 IP，所有人都是 127.0.0.1，审计就废了。所以我优先读 X-Forwarded-For 的第一个 IP，它记录了从客户端到服务端经过的每一跳；没有再退到 X-Real-IP，最后才是 remoteAddr。实测带 X-Forwarded-For 头访问，日志里记到的是真实 IP。
>
> 落库走 **@Async 独立线程池**：一次 insert 几毫秒，但每个写操作都来一条，量很大。放进业务线程会白等一个网络来回，放进 Tomcat 工作线程又会在大批量操作时挤占请求处理能力。独立线程池两边都不占。
>
> 最后两个硬约束：**异常必须原样 rethrow**——切面捕获异常只是为了记失败原因，记完一定要抛回去，否则前端会收到"成功"但实际失败了，这是 AOP 最容易埋的雷；**落库整段 try-catch 吞异常**，日志表写满、连接超时都不能让"新增合约条款"这种主流程挂掉。这条我专门做了验证：把日志表改名让写入必然失败，业务接口照样返回成功。

### 2. 源码对照（被追问时指这里）

| 讲的点 | 文件 | 关键代码 |

### 3. 实测证据（面试说"我验证过"）

`bash verify-operlog.sh 18082` → **PASS=14 FAIL=0**，关键几条：

- 正常请求入库 → 日志 `module=期货合约条款 action=新增 method=FuturesContractTextController.insertText ip=203.0.113.77 cost=327ms success=1`
- **IP 断言用的是伪造的 X-Forwarded-For 头**（203.0.113.77），证明确实优先读代理头而不是 remoteAddr

### 4. 追问应答

- **Q：为什么不用拦截器/过滤器？**
  A：Filter 只能拿到 URL 和请求头，拿不到"这是哪个模块的什么操作";拦截器粒度到 Controller 方法但拿不到方法返回值和具体异常信息。注解+切面可以在**方法级**声明语义（模块、动作），这是 URL 表达不出来的。
- **Q：@Async 为什么不生效的常见原因？**
  A：三个：①同类内部调用（`this.xxx()`）不经过代理；②没配线程池 Bean 或没加 @EnableAsync；③方法不是 public、返回值不是 void/Future。我把它单独放在 OperationLogService 里由切面注入调用，就是为了避开第 ① 条。
- **Q：日志写失败你怎么发现的？**
  A：落库失败打 warn 日志带模块和动作名，运维侧能看到；另外业务完全不受影响，所以是"可观测但不阻断"的设计。
- **Q：敏感字段怎么办？**
  A：**目前源码里没有开关** —— `@OperLog` 只有 `module` / `action` 两个属性，现状是把整段参数序列化后截断 2000 字。
  被追问就如实说这是后续改造点：给注解加一个 `recordParams` 属性，或做一个字段脱敏过滤器。
  （⚠️ 千万别说"我留了 recordParams 开关"—— 源码里没有，面试官让你翻代码会当场翻车。）
- **Q（高频）：你的 AOP 用的是 JDK 动态代理还是 CGLIB？**
  A：**CGLIB**。两条理由各自都足以成立：① Spring Boot 2.x 起 `spring.aop.proxy-target-class` 默认就是
  true（Boot 1.x 才是 false），本项目 yml 没覆盖它；② 被切的 Controller 都不实现接口，
  就算切回 JDK 模式 Spring 也会退化成 CGLIB。有运行时证据：
  `src/test/.../OperLogProxyTest.java` 断言 `AopUtils.isCglibProxy(...)=true`、
  `isJdkDynamicProxy(...)=false`，实际打印的代理类名是
  `FuturesContractTextController$$EnhancerBySpringCGLIB$$180d02ab`。
- **Q：依赖里有 aspectjweaver，那是不是 AspectJ 静态织入？**
  A：**不是**。aspectjweaver 在这里只提供 @Aspect 注解和切点表达式的**解析**，
  真正织入是 Spring AOP 在运行时用 CGLIB 生成子类完成的。真正的 AspectJ 织入要开 LTW 或编译期织入，本项目都没开。
  另外依赖树里看不到独立的 cglib jar——Spring 5 已把 CGLIB 重打包进 spring-core。
- **Q：JDK 代理和 CGLIB 怎么选、各自限制？**
  A：JDK 代理要求目标类**实现接口**，代理类和目标类是兄弟关系，只能代接口方法；
  CGLIB 生成目标类的**子类**，不要求接口。CGLIB 的限制：**final 类、final 方法、private 方法代理不了**
  （子类覆写不了），构造时会各调一次构造器。Spring 5 之后 CGLIB 性能已不输 JDK 代理，
  加上 Boot 2.x 默认 CGLIB，实际大多数项目都是 CGLIB。
  **对本项目的影响**：加 @OperLog 的方法不能是 final/private，否则注解静默失效。

## 四、AI 两大能力（红线：说"自研框架"，别说 "Spring AI"）

### 总起口语版（两条共用，30 秒）

> 我没有直接用 Spring AI，而是自研了一套轻量的 Function Calling 框架：自定义 @Tool 注解标记工具方法，Spring 启动时用 BeanPostProcessor 扫描所有 Bean，把带注解的方法注册进 ToolRegistry；对话时把工具清单（名字、描述、参数）按 OpenAI 的 tools 协议发给 Ollama 上的 qwen2.5 7B 模型。模型判断需要数据就返回 tool_calls，我执行对应方法、把结果作为 OBSERVATION 回灌，模型再基于真实数据作答——保证它答的是库里的数据，不是编的。

### ① 制度知识库问答（RAG + 流式输出）

**一分钟口语版：**

> 场景是用户问"套保制度里保证金怎么规定"这类问题，模型本身不知道我们公司的制度，让它裸答就是瞎编。所以我做了 RAG：
>
> **入库侧**：上传 PDF，先用 PDFBox 解析出全文，再按固定长度加重叠切分——每块 500 字、相邻块重叠 80 字（`chunk-size: 500` / `chunk-overlap: 80`），重叠是为了防止一句话正好被切断、语义丢失。切的时候优先在段落、句子边界断开，避免把一句话腰斩。每个文本块调用本地的 bge-m3 模型转成 1024 维的语义向量，存进 PostgreSQL 的 pgvector 扩展，建了 HNSW 索引，距离用余弦相似度。
>
> **查询侧**：用户提问时，先把问题也转成向量，去 pgvector 里做相似度检索，取最相近的几个文本块；检索结果作为知识库工具的返回值回灌给模型，模型只基于这些片段作答，并且我在提示词里强制它在结尾标注"参考：《文档名》"，做到引用溯源。如果没检索到，明确要求它告知用户知识库暂无，禁止编造。
>
> **流式输出**：本地 7B 模型生成一段回答要几十秒，一次性返回的话用户盯白屏。我用 SSE（SseEmitter）做逐 token 推送。这里有个关键取舍：**链路分两个阶段**——工具阶段必须非流式，因为要拿到模型完整的 tool_calls 才知道执行哪个工具；工具结果回灌后进入生成阶段，这时把工具定义**摘掉**（否则模型可能又发起一轮工具调用），用 stream=true 逐 token 输出最终答案。整条链路丢到 @Async 独立线程池跑，不占 Tomcat 工作线程。实测首字 7 秒多到达，后面 30 多个增量块连续吐出，体感接近打字机。

**源码对照：**

| 讲的点 | 文件 |
|-------|------|
| 上传→解析→切分→向量化→入库 编排与状态机（PENDING→PARSING→INDEXED/FAILED，失败清分块不留半成品） | `ai/rag/KnowledgeService.java` |
| 中文分块（chunkSize + overlap） | `ai/rag/TextChunker.java` |

**追问应答：**

- **Q：为什么用 pgvector 不用 Milvus/ES 向量检索？**
  A：数据量是几百到几千个分块，pgvector 的 HNSW 索引完全够，还省一个独立中间件——PostgreSQL 一个容器同时管元数据和向量，运维成本最低。量级到千万级向量再上专用向量库。
- **Q：为什么要重叠切分？**
  A：不重叠的话，关键句恰好跨块边界就两边都不完整，检索命中了也答不全。重叠 20% 左右是常见取舍。
- **Q：为什么生成阶段要把工具定义摘掉？**
  A：实测不摘的话模型有一定概率再发起一轮工具调用，又走一遍非流式请求，用户多等几十秒还看不到字；摘掉后它只能基于已有信息作答，正好也是我们想要的。
- **Q：向量库挂了会怎样？**
  A：PgVectorStore 初始化失败只打 WARN 不阻塞应用启动；检索时返回空结果降级为普通对话。另外它故意不注册成 Spring 的 DataSource Bean——一旦注册，Spring Boot 的数据源自动装配会退让，MySQL 主数据源就失效了，这是我踩过的一个真实坑。
- **Q：SseEmitter 超时怎么定的？**
  A：取大模型读超时的两倍。本地 7B 单轮推理就可能几十秒，默认超时会在出答案前被容器掐断。

### ② 合约文本自动解析入库（AI 写操作）

**一分钟口语版：**

> 场景：业务上经常要把一份合约条款的 Word/PDF 文字录入系统，纯手工填十几个字段。我做的是把原文直接发给模型，模型从中抽取结构化字段（合约代码、品种、交易所、交易单位、保证金……），然后调用我注册的 @Tool 工具入库。
>
> 因为这是全项目唯一一个**带写操作**的 AI 能力，直接让模型写库风险很大，我设了三道闸门：
>
> 第一，**两段式**：拆成"预览"和"保存"两个工具。模型只能先调预览，预览工具只做校验和展示，绝不写库；用户确认后才允许保存。
>
> 第二，**服务端一次性令牌**：预览通过后服务端生成一个 10 分钟有效、用后即焚的 previewToken，字段内容存在服务端缓存里；保存工具只收令牌，入库字段全部从服务端缓存取，不从模型参数取。这样"模型跳过预览直接写库"在服务端就不可能发生——不靠提示词约束模型自觉，靠机制。同时保证用户确认的字段和实际入库的字段严格一致，避免 7B 模型第二轮调用时把 14 个字段抄错一两个。
>
> 第三，**字典校验**：合约代码、品种、交易所必须在系统里真实存在才放行——既是防脏数据，也是因为底层插入依赖这些关联 id，匹配不上直接失败。校验不通过时把系统里已有的可选值列给模型，让它引导用户修正而不是瞎猜。
>
> 写库走的是和普通业务完全一样的 insertText 方法，所以自动享受 ES 双写和重试补偿——AI 录的数据也能立刻被 ES 搜到，链路是闭环的。

**源码对照：**

| 讲的点 | 文件 |
|-------|------|
| 预览/保存两工具 + 三道闸门全部逻辑 | `ai/tool/impl/ContractImportTools.java`（preview 14 参数只读校验；save 只收 token；`pending` ConcurrentHashMap 存令牌；`purgeExpired()` 清过期） |
| 防重复提交 | 同上：`pending.remove(token)` 用掉即删，伪造/重复 token 一律拒绝 |
| 字典校验带可选值回显 | 同上：`availableVarieties()` / `availableExchanges()` |
| HTTP 入口（可 dryRun） | `ai/controller/ContractImportController.java` → `POST /api/ai/contract/import` |
| 复用业务写入（享受 ES 双写） | 调 `IFuturesContractTextService.insertText(dto)` |
| 提示词硬约束 | `resources/system-prompt.txt`（"写入前必须 preview 确认，禁止直接写库"） |

**追问应答：**

- **Q：为什么不信任模型、把校验放服务端？**
  A：7B 本地模型能力有限，提示词说"必须先预览"它偶尔会跳；令牌机制让它跳不了——save 只认服务端发过的 token，没预览就没有 token。安全上叫"不信任边界外的输入"。
- **Q：令牌为什么存内存而不是 Redis？**
  A：当前单体部署、10 分钟 TTL、量小，ConcurrentHashMap 够用且零依赖。要上集群或量大再换 Redis，接口不用动。
- **Q：AI 写的数据怎么保证也能被搜到？**
  A：insertText 是业务 Service 的方法，ES 双写挂在它的事务提交后，AI 走这条路就自动同步。ES 挂了就走重试表，最终能搜到。

### ③ 工具能按用户的条件查库吗？—— 能力清单与边界（2026-09-27 实测）

**一句话答案**：能。Function Calling 里模型**不写 SQL**，它做的是"选工具 + 填参数"；
所以**能用的条件 = 工具方法签名上预定义的那些参数**，而不是任意 SQL 条件。

**六个工具**（`GET /api/ai/tools` 实时可查）：

| 工具 | 参数 | 类型 | 底层做什么 |
|------|------|------|-----------|
| `queryFuturesContractSpec` | keyWord | 查询 | 合约条款：5 表 join，keyWord 同时 OR 匹配 品种名/合约代码/交易所名/行业名 |
| `queryFuturesContract` | varietyName | 查询 | 合约列表：按品种名模糊匹配 |
| `querySpotProduct` | spotName | 查询 | 现货：全表取出后内存过滤名称/规格 |
| `searchKnowledgeBase` | query, topK | 查询 | RAG：pgvector 余弦相似度 Top-K |
| `previewFuturesContractText` | 14 个字段 | 写·预览 | 只读 + 品种/交易所字典校验 + 发一次性 token |
| `saveFuturesContractText` | previewToken, contractCode | 写·落库 | 校验 token 后落库（复用业务 Service，自动享受 ES 双写） |

**实测记录**（`bash verify-fc-query.sh 18081` → PASS=15 FAIL=0）：

| 用户问 | 模型选的工具与参数 | 结果 |
|--------|------------------|------|
| 螺纹钢的保证金比例是多少 | `queryFuturesContractSpec(keyWord=螺纹钢)` | ✅ 合约价值的 6% |
| 螺纹钢属于哪个交易所 | `queryFuturesContract(varietyName=螺纹钢)` | ✅ 郑州商品交易所 |
| 螺纹钢有哪些合约、最后交易日 | `queryFuturesContract(varietyName=螺纹钢)` | ✅ RB2610 / 2026-10-15 |
| 有哪些属于黑色金属的品种 | `queryFuturesContract(varietyName=黑色金属)` ← **选错工具** | ⚠️ 答"未检索到"（同一份数据换个 keyWord 走条款工具能查到 1 条） |
| 保证金比例超过 10% 的品种有哪些 | `queryFuturesContractSpec(keyWord="")` | ❌ 工具报"参数不能为空" |

**边界（面试主动说出来，别等被问）**：

1. **只支持预定义参数** —— 每个查询工具就 1 个字符串参数，条件集合是我定的，模型只能填值。
2. **不支持范围比较** —— `>` `<` `between` 表达不了。要支持就把比较条件做成参数（阈值 + 操作符），仍不让模型碰 SQL。
3. **不支持聚合/排序** —— 没有 count/sum/group by 工具；结果上限 `MAX_ROWS=10`，分页参数也没暴露给模型。
4. **模糊匹配 ≠ 精确条件，且选错工具就查不到** —— "黑色金属"那条就是：数据在，工具选错 + 参数语义错配 → 0 条。
5. **模型会编** —— 工具没返回的字段它会用先验知识补（实测把库里的郑州商品交易所答成上海期货交易所），
   纯业务查询也会硬加「参考：《不存在的文档》」。

**本轮实测暴露并修复的 4 个真 bug**（面试可讲"问题是我自己测出来的"）：

| 问题 | 现象 | 修复 |
|------|------|------|
| 合约条款实体漏映射 `exchange` | 工具返回里没有交易所字段 → 模型只能凭先验知识编"上海期货交易所" | `dao/FuturesContractTextMapper` 补 `@Result(property="exchange", column="exchange_id", one=@One(...ExchangeMapper.findById))` |
| 合约列表按品种名是**等号精确匹配**，且空值恒返回 0 条 | 工具描述写着"不传则返回全部前若干条"，实际一条都查不到 | SQL 改成 `(#{varietyName} is null or #{varietyName}='' or tv.variety_name like ...)`，与同文件 keyWord 的写法保持一致 |
| native 模式下模型把工具调用**吐成文本** | 日志 `rounds=1, toolCalls=0`，原始 JSON 被当作答案返回给用户 | `LlmClient.parseLeakedToolCall()` 兜底解析，且**要求 name 命中本次下发的工具名**才认，避免误判正常 JSON 回答 |
| 业务数据查询**伪造来源标注** | "螺纹钢在郑州商品交易所上市。参考：《期货合约信息列表》"——该文档不存在 | `ChatService.sanitizeCitation()`：本轮没调 `searchKnowledgeBase` 就把标注删掉；流式路径加 24 字符末尾保留窗口 |

**追问应答：**

- **Q：模型自己写 SQL 吗？**
  A：不写。工具方法的入参就是白名单条件，模型只能填值。让它生成 SQL 既有注入风险，执行计划也不可控。
- **Q：那"保证金大于 10%"这种怎么支持？**
  A：加一个工具方法，把阈值和比较符作为参数，SQL 在服务端拼——条件仍然由我定义，模型只负责填数字。
- **Q：为什么不用 ES 做这些查询？**
  A：这里要的是"命中即精确"的条件过滤，MySQL 走索引更快也更简单；ES 负责中文全文检索与分词。两者分工，不互相替代。
- **Q：模型答错了怎么办？**
  A：三层防护——① 工具返回真实数据；② 提示词要求"以工具返回为准，工具没返回的字段就说暂无数据"；
  ③ 服务端再过滤伪造引用（`sanitizeCitation`）。三层的顺序是"先给它真数据，再约束它，最后兜底"。
