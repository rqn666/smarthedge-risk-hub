# 操作日志 AOP —— 逐行白话讲解

> 写给"看得懂业务代码、但对 AOP 不熟"的自己。目标：能讲清楚每一行在干什么，不是背术语。

---

## 0. 先说结论：这功能一共就 3 个文件

| 文件 | 干什么 | 大概几行 |
|------|--------|---------|
| `annotation/OperLog.java` | 一张"便利贴"，贴在方法上写清楚"这是哪个模块的什么操作" | 6 行 |
| `aspect/OperLogAspect.java` | **核心**：拦住贴了便利贴的方法，记录日志 | 主流程只有 20 行 |
| `service/OperationLogService.java` | 把日志写进数据库，异步的、失败也不影响业务 | 有效代码 10 行 |

再加一个线程池配置文件 `configure/OperLogAsyncConfig.java`（8 行，就是配个线程池参数）。

**用的时候只需要在 Controller 方法上加一行：**

```java
@OperLog(module = "期货合约条款", action = "新增")
@PostMapping("/insertText")
public Result insertText(@RequestBody FuturesContractTextAddDTO dto) {
    int i = futuresContractTextServiceImp.insertText(dto);
    return i>0 ? Result.success(null) : Result.fail(500,"请重新尝试");
}
```

方法里面**一行日志代码都没写**，日志自动就记下来了。这就是这套东西的全部价值。

## 1. 核心：主流程 20 行（唯一要背的）

```java
@Around("@annotation(operLog)")
public Object doLog(ProceedingJoinPoint pjp, OperLog operLog) throws Throwable {

    // ① 方法执行前：先把要记的东西准备好
    HttpServletRequest request = currentRequest();   // 当前这次 HTTP 请求
    String ip = clientIp(request);                   // 客户端 IP
    String params = paramsToJson(pjp.getArgs());     // 方法入参转成 JSON
    long start = System.currentTimeMillis();         // 开始计时

    try {
        // ② 执行真正的业务方法（这一行就等于原来那个 Controller 方法本身）
        Object result = pjp.proceed();

        // ③ 没抛异常 = 成功 → 异步记一条成功日志（丢给线程池，不等它写完）
        logService.saveAsync(buildLog(operLog, pjp, request, ip, params, start, 1, null));
        return result;

    } catch (Throwable e) {
        // ④ 抛异常 = 失败 → 记一条失败日志，把异常原因也存下来
        logService.saveAsync(buildLog(operLog, pjp, request, ip, params, start, 0,
                e.getClass().getSimpleName() + ": " + e.getMessage()));

        // ⑤ 关键：异常必须原样抛回去，绝不能吞掉
        throw e;
    }
}
```

### 逐行白话

| 行 | 白话解释 |
|----|---------|
| `@Around("@annotation(operLog)")` | "凡是贴了 @OperLog 便利贴的方法，都先过我这一关" |
| `ProceedingJoinPoint pjp` | 代表"被拦住的那个方法"。可以从它身上拿到方法名、参数 |
| `OperLog operLog` | 那张便利贴本身，能读到上面写的 module 和 action |
| `currentRequest()` | 拿到这次 HTTP 请求，后面要从请求头里取 IP |
| `clientIp(request)` | 取客户端 IP（下面第 3 节细说，这里有个坑） |
| `paramsToJson(pjp.getArgs())` | 把方法收到的参数转成 JSON 字符串，方便以后查"当时传了什么" |
| `start = ...millis()` | 记个开始时间，等下用"现在时间 - 开始时间"算耗时 |
| **`pjp.proceed()`** | **最关键的一行：放行，让真正的业务方法去执行。** 上面是"方法执行前"，下面是"方法执行后" |
| `saveAsync(... 1, null)` | 成了：丢一条"成功"日志给线程池，参数是 1=成功、null=没错误原因 |
| `catch (Throwable e)` | 业务方法抛异常了 = 这次操作失败 |
| `saveAsync(... 0, "...")` | 败了：丢一条"失败"日志，把异常类型和原因存进 error_msg |
| **`throw e`** | **必须把异常原样抛回去。** 我 catch 它只是为了记录，不是要替业务兜着。不抛回去的话，前端收到的就是"操作成功"但实际数据没写进去——这是最坑的 bug |

### 一句话总结主流程

> **进来记时间 → 放行让方法执行 → 成功记成功、失败记失败 → 异常一定抛回去。**

就这一句，剩下全是打杂。

## 2. 注解：它就是一张便利贴

```java
@Target(ElementType.METHOD)            // 只能贴在方法上
@Retention(RetentionPolicy.RUNTIME)    // 运行时还得能读到（切面靠反射读它）
public @interface OperLog {
    String module();   // 业务模块，比如 "期货合约条款"
    String action();   // 操作类型，比如 "新增"
}
```

**为什么非得有个注解？** 因为程序得知道"当前这个方法到底是干啥的"。不加注解，切面只能看到 `insertText` 这个方法名，**不知道它属于哪个模块、算新增还是修改**。注解就是把这个信息告诉它。

去掉注解行不行？行，但得换成别的约定——比如"方法名以 insert 开头算新增、delete 开头算删除"，那反而更绕、更爱出错。

## 3. 取 IP 那个坑（面试爱问）

```java
private String clientIp(HttpServletRequest request) {
    String xff = request.getHeader("X-Forwarded-For");
    if (xff != null && !xff.trim().isEmpty()) {
        return xff.split(",")[0].trim();     // 格式 "真实IP, 代理1, 代理2"，第一个才是用户
    }
    String real = request.getHeader("X-Real-IP");
    if (real != null && !real.trim().isEmpty()) {
        return real.trim();
    }
    return request.getRemoteAddr();
}
```

**为什么不能直接 `request.getRemoteAddr()` 完事？**

因为应用一旦挂在 Nginx 后面，请求是 Nginx 转发过来的，`getRemoteAddr()` 拿到的是 **Nginx 的 IP**，所有人记下来都是 `127.0.0.1`，那这个日志就废了——出了事你根本不知道是谁干的。

`X-Forwarded-For` 这个头记录了请求从用户浏览器到服务器经过的每一跳，第一个才是真实用户 IP。

> 验证证据：验收脚本发请求时带了一个假头 `X-Forwarded-For: 203.0.113.77`，日志里记到的确实是 `203.0.113.77`，而不是 127.0.0.1。

## 4. 异步落库：为什么不等它写完

```java
@Async("operLogExecutor")          // 交给专门的线程池去跑
public void saveAsync(OperationLog record) {
    try {
        operationLogMapper.insert(record);
    } catch (Exception e) {
        // 只打日志，绝不往外抛
        log.warn("[operlog] 操作日志写入失败 ...: {}", e.getMessage());
    }
}
```

**为什么异步？** 一次插入就几毫秒，但每个写操作都来一条，量很大。放在业务线程里会白白多等一个网络来回；放在处理 HTTP 请求的线程里，大批量操作时又会挤占请求处理能力。所以单独给它一个线程池。

**为什么 catch 掉不抛？** 日志是"附属功能"。日志表满了、数据库抖了一下，都不能让"新增合约条款"这种正经业务失败。

> 验证证据：验收脚本有一组专门测这个——把日志表改名让写入必然失败，业务接口照样返回 `success:true`。

## 5. 完整链路（文字版流程图）

```
浏览器发请求 POST /api/futureContractText/insertText
        ↓
Spring 拿到的是【代理对象】（CGLIB 生成的子类，类名带 $$EnhancerBySpringCGLIB$$）
        ↓
代理对象先走切面 doLog()
        ↓
   记下 IP、参数、开始时间
        ↓
   pjp.proceed()  →  执行真正的 Controller 方法（查库、写库、同步 ES…）
        ↓
   回到切面，算耗时，组装日志对象
        ↓
   丢给线程池异步写 sys_oper_log（主线程不等它）
        ↓
返回响应给浏览器
```

**代理是谁生成的？CGLIB。** 不是 JDK 动态代理。理由两条：① Spring Boot 2.x 默认就用 CGLIB；② 这几个 Controller 都没实现接口，JDK 代理根本没接口可代。实证类名：

```
FuturesContractTextController$$EnhancerBySpringCGLIB$$180d02ab
```

## 6. 面试照着念（30 秒版）

> 我用 Spring AOP 做了操作日志，做法很简单：自定义一个 @OperLog 注解，写清楚模块名和动作名，贴在 Controller 方法上，方法里面一行日志代码都不用写。
>
> 切面用环绕通知，进来先记下 IP、参数和时间，然后放行让业务方法执行，执行完算耗时，成功记成功、抛异常记失败，最后**异常一定原样抛回去**——不然前端会收到"成功"但实际是失败的。
>
> 落库是异步的，走独立线程池，日志写失败只打 warn 不影响业务。IP 那里我专门处理过：挂在 Nginx 后面时 getRemoteAddr 拿到的是 Nginx 的 IP，所以优先读 X-Forwarded-For。
>
> 底层代理是 CGLIB，因为 Boot 2.x 默认就是它，而且我的 Controller 都没实现接口。

### 追问怎么答

| 追问 | 答 |
|------|-----|
| 为什么用环绕通知？ | 开始时间得存在一个地方。用三个通知拼就得存成员变量，切面是单例，并发下会串。环绕通知用局部变量，天生安全。 |
| 异常为什么还要抛？ | 我 catch 只是为了记失败原因。吞掉的话前端收到"成功"但数据没写进去，是最坑的 bug。 |
| JDK 代理还是 CGLIB？ | CGLIB。Boot 2.x 默认 proxyTargetClass=true，而且 Controller 没实现接口。实证类名里带 `$$EnhancerBySpringCGLIB$$`。 |
| 引了 aspectjweaver 是不是 AspectJ 织入？ | 不是。它只负责解析 @Aspect 注解和切点表达式，织入还是 Spring AOP 运行时用 CGLIB 生成子类。而且不用引第三方 cglib 包，Spring 5 已经把 CGLIB 打包进 spring-core 了。 |
| 日志写失败会怎样？ | 只打 warn，业务照常。我专门验证过：把日志表改名，业务接口照样返回成功。 |
