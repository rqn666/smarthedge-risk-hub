## B. 主力亮点（能扛追问的 9 个）

### 1. 自研 Function Calling 框架（零 Spring AI 依赖）★最推荐写
- `@Tool` / `@ToolParam` 自定义注解 + `BeanPostProcessor` 启动自动扫描注册（拿到的是 Spring 代理对象，AOP 仍生效）【`ai/tool/ToolRegistry.java`】
- `maven-compiler-plugin` 开 `-parameters`，否则反射拿到 `arg0/arg1`，`@ToolParam` 机制直接失效【`pom.xml`】
- 反射调用 + 字符串参数按目标类型转换；异常兜成可读文本回灌给模型，让它自己改参数重试【`ai/tool/ToolExecutor.java`】
- LLM → 工具 → `OBSERVATION` 回灌 → 再问 LLM 的多轮闭环，`maxToolRounds` 上限后摘掉工具强制出结论【`ai/chat/ChatService.java`】

### 2. 双模式 LLM 协议适配
- `native`：走 OpenAI `tools[]` + `tool_choice=auto` 协议
- `prompt`：工具清单写进 system，让模型吐 JSON、后端解析（给不支持 tools 的 deepseek-r1 兜底）【`ai/client/LlmClient.java`】

### 3. MySQL ↔ ES 双写一致性（最像"高级工程师"的一条）
- **事务提交后才写 ES**：`TransactionSynchronizationManager` + `afterCommit` 回调，
  避免"事务回滚了但 ES 已写入"的脏数据【`es/sync/EsWriteHelper.java`】
- **失败落重试表**：`es_retry_task`，`PENDING/SUCCESS/DEAD` 状态机 + `retry_count/max_retry`【`es/sync/EsSyncService.java`】
- **定时补偿**：`@Scheduled(fixedDelay)` 扫 PENDING，单批限流 100 条【`es/sync/EsRetryScheduler.java`】
- **补偿时从 MySQL 反查最新，而不是重放旧文档**（失败后数据可能又被改过）；
  反查不到说明业务已删 → 转成删 ES 文档，**自愈**【同上】
- **幂等**：ES 文档 `_id` 一律用业务主键，重复写即覆盖；delete 不存在也算成功

### 4. 多级降级 / 不阻塞设计
- `ApplicationRunner` 启动自检建索引，ES 连不上**只打日志不抛异常**，应用照常启动【`es/config/EsIndexInitializer.java`】
- 搜索失败返回 `503 + "请降级走数据库查询"`，引导调用方回退，而不是 500【`es/controller/EsSearchController.java`】
- 双写异常全吞 + 兜底，主业务绝不受影响（定位：ES 是加速层，不是数据源）

### 5. RAG 私有知识库问答（完整落地）★★可重点写
- **文档解析**：PDFBox 抽文字，`setSortByPosition(true)` 防双栏乱序；
  显式识别"扫描件无文字层"（否则会建出一个上传成功却检索不到的空文档）；
  中文 txt 走 UTF-8 严格解码、失败自动退 GBK【`ai/rag/DocumentParser.java`】
- **中文分块**：优先段落 → 句子边界断开（硬切会把"保证金比例为合约价值的 6%"腰斩），
  chunk 间保留 overlap（500/80），且**绝对防死循环**；
  额外修掉"PDF 硬换行被误当句子边界"——PDF 按视觉行换行，`…统一加收 2` + `个百分点…`
  会被切成半句话，两块都检索不到【`ai/rag/TextChunker.java`】
- **批量向量化**：Ollama `/api/embed` 批量接口（老 `/api/embeddings` 一次只吃一条，200 块要发 200 次 HTTP）；
  维度 1024 不匹配直接报错；失败不吞异常，必须让上层把文档标 FAILED【`ai/rag/EmbeddingClient.java`】
- **向量库**：PostgreSQL + pgvector，`vector(1024)` + **HNSW 索引 + `vector_cosine_ops` 余弦距离**，
  `kb_document` 状态机 `PENDING→PARSING→INDEXED/FAILED`【`sql/pgvector_knowledge.sql`】
- **入库编排**：单事务批量写 chunk（避免写一半留脏数据）；上传路径做**路径穿越防护**；
  文档落盘并记 `file_path`，支撑"重传/重建索引"【`ai/rag/KnowledgeService.java`】
- **接入 Function Calling**：检索封装为 `@Tool searchKnowledgeBase`，模型**自主判断**何时调用，
  回灌时带 chunk 原文 + 文档名，支持引用溯源（`参考：《文档名》`）【`ai/tool/impl/KnowledgeTools.java`】
- **工程细节（面试可讲）**：pgvector 连接池**不注册成 Spring Bean** —— 自建 `DataSource` Bean 会让
  Boot 的 `DataSourceAutoConfiguration` 因 `@ConditionalOnMissingBean` 整体退让，
  把 MyBatis-Plus 的 MySQL 数据源搞坏；改为组件私有字段持有【`ai/rag/PgVectorStore.java`】

### 6. 防幻觉 / 可观测
- 工具结果以 `OBSERVATION:` 回灌，并要求"不要编造数据"
- 模型自造 `result` 字段 → 直接丢弃并告警【`LlmClient.java`】
- 接口返回 `toolTrace`：每次工具调用的 round / 参数 / 结果 / 耗时，前端可展示"模型调了什么"【`ai/controller/AiChatController.java`】
- 全链路耗时埋点（LLM 调用、工具执行、ES 搜索 cost）

### 7. SSE 流式输出（工具阶段非流式 + 生成阶段流式）★★可重点写
- **核心取舍**：OpenAI tools 协议必须先拿到完整 `tool_calls` 才能执行，"边流边调"做不到。
  所以拆成「工具阶段非流式 + 生成阶段流式」，且生成阶段**必须摘掉工具定义** ——
  否则模型可能再发起一轮工具调用，答案永远出不来【`ai/chat/ChatService.java`】
- **流式必须用 `RestTemplate.execute` 直读响应流**，不能用 `postForEntity`——
  后者会把整个响应缓冲完再返回，逐块读取的效果就没了【`ai/client/LlmClient.java`】
- **工具轮次单独配置**（`stream-tool-rounds` 默认 1）：每多判断一轮就多一次几十秒的阻塞推理，
  用户全程看不到字，流式就白做了【`application.yml`、`AiProperties.Llm`】
- **SSE 事件设计**：`tool_start` / `tool_end` / `delta` / `done` / `error`，
  前端能实时展示"模型正在调哪个工具、花了多久"【`ai/controller/AiChatController.java`】
- **独立线程池** `@Async("aiExecutor")`：一次对话几十秒，占着 Tomcat 工作线程会拖垮 Web 容器；
  拒绝策略用 CallerRuns（队列满时退回调用线程，宁可慢不丢请求），不用无界队列【`ai/config/AiAsyncConfig.java`】
- **编排层不耦合 Web 类型**：抽出 `StreamListener` 回调接口，Controller 负责适配成 SSE，
  单测里可以塞假实现【`ai/chat/StreamListener.java`】
- **实测**：33 个 delta 块逐块到达（`t+7.6s 螺` → `t+7.7s 纹` → `t+7.8s 钢`…），首字 7.63s，总耗时 11s

### 8. AI 写操作：合约文本解析入库（唯一带写库的 AI 能力）★★可重点写
- **三道闸门**：①preview / save 拆两步；②**服务端强制一次性令牌**；③入库前字典校验
- **令牌机制的价值**：save 必须携带 preview 发放的 token，服务端**只从令牌缓存取字段入库**。
  于是"模型跳过预览直接写库"在服务端根本不可能发生 —— **不依赖模型自觉遵守提示词**，
  且保证「用户确认的字段」与「实际入库的字段」严格一致。
  save 因此只有 2 个参数（token + 合约代码），避免 7B 模型抄错 14 个字段
- **为什么必须做字典校验**：底层 `insertText` 依赖 varietyId / exchangeId，
  匹配不上直接 NPE；同时这也防住了"AI 把保证金 6% 抽成 60%"之外的关联数据脏化
- **失败可自愈**：preview 校验不通过时返回 `missingRequired` / `dictErrors`，
  模型能据此改参数重试；令牌一次性，重复提交被拒
- **写入后自动带 ES 双写**（走 Service，不在工具里单独写索引）
- **实测**：自然语言 → AI 抽 14 个字段 → preview 校验通过 → 用户确认 → 落库 → ES 可检索

### 9. AOP 操作日志（注解驱动 + 异步落库）★好讲、代码量小
- **零侵入**：业务方法只加一行 `@OperLog(module="期货合约条款", action="新增")`，方法体内不写任何日志代码【`annotation/OperLog.java`】
- **用 @Around 不用三个通知拼**：开始时间存在方法局部变量里；分开写要存成员变量，而切面是单例，并发下 A 请求的开始时间会被 B 覆盖
- **异常必须原样 rethrow**：catch 只为记录失败原因，吞掉后前端收到"成功"但数据没写进去 —— 专门加了断言【`aspect/OperLogAspect.java`】
- **IP 三级取值**：`X-Forwarded-For` → `X-Real-IP` → `getRemoteAddr`（挂 Nginx 后只写 remoteAddr 会全是 127.0.0.1，审计失效）
- **异步落库**：`@Async("operLogExecutor")` 独立线程池（core2/max4/queue500/CallerRuns），入库整段 try-catch 只打 warn【`service/OperationLogService.java`】
- **底层是 CGLIB**：Spring Boot 2.x 起 `proxy-target-class` 默认 true，且三个 Controller 都不实现接口；运行时代理类名实测为 `$$EnhancerBySpringCGLIB$$`，有单测钉死【`src/test/.../OperLogProxyTest.java`】
- **实测**：`verify-operlog.sh` 14/14 通过；把日志表改名让写入必然失败时，业务接口照常返回成功

## E. 可直接粘贴的简历项目描述

> 下面是成品，整段可复制。括号里的数字按你实际情况改。

**SmartHedge 大宗商品套保风险中台 | Java 后端 | 2026.09 - 至今**

- 面向大宗商品套期保值场景的风险数据中台，统一管理期货/期权合约、合约条款、现货商品、供应商与分类等（6 类）业务数据，
  提供多维度检索与 AI 智能问答能力。
- **自研 Function Calling 框架**：不依赖 Spring AI，基于 `@Tool`/`@ToolParam` 自定义注解 + `BeanPostProcessor`
  实现工具自动注册（保留 Spring 代理使 AOP 生效），反射执行并按目标类型做参数转换；
  实现 LLM→工具→OBSERVATION 回灌→再推理的多轮闭环，轮次超限时摘除工具强制出结论。
  支持 OpenAI `tools` 原生协议与 JSON 提示词双模式，兼容不支持 tools 的推理模型。
- **MySQL 与 ES 双写一致性方案**：基于 `TransactionSynchronization#afterCommit` 保证事务提交后才同步 ES，
  规避回滚导致的脏数据；双写失败落 `es_retry_task` 重试表，由 `@Scheduled` 补偿任务按批限流重放，
  补偿时回源 MySQL 反查最新数据（而非重放旧文档），数据已删则转为删除 ES 文档实现自愈；
  文档 `_id` 采用业务主键保证幂等，重试次数超限标记 DEAD 等待人工介入。
- **多级降级设计**：ES 启动自检失败不阻塞应用启动，搜索异常返回 503 引导调用方回退数据库查询，
  定位 ES 为加速层而非数据源，任一环节故障不影响主业务写入。
- **检索相关性调优**：`multi_match` 采用 `cross_fields` 解决多词跨字段零召回问题，叠加 PHRASE 查询提权，
  对品种名/合约名等业务字段配置 1.5~3 倍权重；全量同步按 500 条/批 bulk 写入并显式 refresh 保证一致性校验准确。
- **RAG 私有知识库问答**：基于 PostgreSQL + pgvector 搭建企业私有知识库，打通「上传 → PDFBox 解析
  （识别扫描件无文字层、中文 GBK/UTF-8 编码兜底）→ 自研中文分块（段落/句子边界优先 + 重叠窗口 + 防死循环）
  → 本地 Ollama `bge-m3` 批量向量化（1024 维）→ 入 pgvector 建 HNSW 余弦索引 → 检索召回」全链路；
  检索封装为 Function Calling 工具由大模型自主调用，回答回带命中原片段并标注「参考：《文档名》」，
  知识库无相关内容时明确告知"未检索到"而非编造。实测检索响应 73~108ms。
- **SSE 流式问答（含 Function Calling）**：实现「工具阶段非流式 + 生成阶段流式」两段式编排 ——
  tools 协议必须先拿到完整 `tool_calls` 才能执行，故工具阶段同步调用、生成阶段摘掉工具后以
  `stream=true` 逐 token 推送；基于 `RestTemplate.execute` 直读响应流（`postForEntity` 会整体缓冲、
  毫无流式效果），并上报 tool_start / tool_end / delta / done / error 事件供前端展示调用轨迹；
  对话跑在独立线程池（`@Async` + CallerRuns 拒绝策略），避免长耗时推理占满 Tomcat 工作线程。
  实测 33 个增量块逐块到达，首字 7.63s。
- **AI 合约文本解析入库**：向模型发送自然语言合约条款，由模型抽取结构化字段并自主调用 `@Tool`
  工具落库。设计三道闸门保证写操作安全：①拆 preview / save 两步；②`save` 必须携带 preview
  发放的**一次性令牌**，服务端只从令牌缓存取字段入库，"跳过预览直接写库"在服务端不可能发生，
  同时保证「用户确认的字段」与「实际入库的字段」严格一致；③入库前做品种 / 交易所 / 合约代码
  字典校验（否则底层关联 id 为空会直接失败）。产出 `verify-ai2.sh` 12 条断言（含伪造、重复令牌被拒）。
- **注解驱动的操作日志**：基于 Spring AOP + 自定义 `@OperLog` 注解实现操作留痕，业务方法只需声明模块与动作，
  由环绕通知统一采集方法名、请求参数、客户端 IP、耗时与执行结果；日志经 `@Async` 独立线程池异步落库，
  与主流程解耦，且落库失败只告警不回传，实测日志表写入失败时业务接口仍正常返回；已覆盖
  期货合约 / 合约条款 / 供应商三个模块的 8 个写操作接口。

## G. 高频追问：「为什么不用 Spring AI，要自己造？」

### 硬结论：不是不想用，是引不进来

Spring AI **1.0.x（GA）官方硬性要求**：`JDK 17+` + `Spring Boot 3.1+`（官方推荐 3.4.x / 3.5.x）。
社区实测兼容矩阵里，Spring Boot **2.7.x 一栏直接写"不支持"**（2.7 时代只对应 0.1~0.4 的远古版本，
无 RAG 工具链；0.7.x 已停止维护且仍有 CVE，且 0.7.1 起就要求 JDK 17）。

本项目 pom 锁的是 **Spring Boot 2.7.15 + `java.version=8`**，`(JDK8, Boot2.7, SpringAI)` 这个组合**不存在可行版本**。
所以自研不是偏好问题，是约束下的唯一解。

### 就算能升，自研这几处也确实更合适（可讲的技术理由）

1. **升级代价远大于收益**：Boot 2→3 要全量迁 `javax.*` → `jakarta.*`，
   本项目还锁着 MyBatis-Plus 3.5.1 与 ES HighLevelClient 7.16.2（版本是被刻意锁死防不匹配的），
   为一个 AI 框架做全栈升级，企业项目不会批。
2. **双模协议是自研才做得到的**：`deepseek-r1` 不支持原生 tools，
   Spring AI 的 tool calling 依赖模型原生 function calling；本项目额外做了"工具清单写进 system + 后端解析 JSON"的兜底模式。
3. **轻量可控**：不引入 spring-ai BOM 与一堆自动配置，包体、启动速度、依赖冲突面都小。

### 但也要承认 Spring AI 确实更强的地方（别把话说满）

| 能力 | Spring AI | 本项目现状 |
|---|---|---|
| RAG 入库 + 召回 | `PgVectorStore` + ETL pipeline（`PagePdfDocumentReader`→`TokenTextSplitter`→写入）开箱即用 | **已自研实现**（解析/分块/向量化/入库/召回/工具接入全通），代价是自己写了约 5 个类 |
| 多轮记忆 | `ChatMemory` / `MessageChatMemoryAdvisor` | 无（每次单轮） |
| 流式输出 | `Flux` + SSE 自动装配 | 无（`stream:false`） |
| 可观测 | 自动埋 LLM 延迟、token 消耗、失败率 | 只有手写耗时日志 |
| 多模型切换 | 统一 `ChatModel` 抽象 | 手写一个客户端，靠 yml 切 |

### 给你的三条路（务实建议）

- **方案 A｜保持自研（推荐，0 成本）**：把"JDK8/Boot2.7 引不了 Spring AI，所以自研"写进简历，
  反而能证明你懂框架原理（BeanPostProcessor、反射、协议适配），比"我调了个 starter"有分量得多。
- **方案 B｜另起小项目拿标签（1~2 天）**：单独开一个 `JDK 17 + Boot 3.4 + Spring AI 1.0.x` 的小项目，
  做"上传 PDF → PgVectorStore → 检索增强问答"，简历上就能名正言顺写 Spring AI。**别动这个老项目**。
- **方案 C｜升级老项目（不推荐）**：javax→jakarta + 组件全量换版本，风险高、收益低。

> ⚠️ 前提：简历上写"熟悉 Spring AI"必须真能讲出 `ChatClient.Builder` / `Advisor` / `VectorStore` / `ToolCallback`，
> 否则不如写"自研 Function Calling 框架"——后者你每一行代码都答得上来。

## H. MyBatis-Plus 能写到什么程度？（逐文件核查结论）

### 用了什么（都有源码实锤）

| 能力 | 证据 |
|---|---|
| `BaseMapper<T>` 基础 CRUD | 13 个 Mapper 全部 `extends BaseMapper`【`dao/`】 |
| MP 通用 Service：`IService` + `ServiceImpl` | `OptionContractTextServiceImp`、`FuturesContractTextServiceImp`、`OperatorServiceImpl`、`OriginDictServiceImpl`、`SupplyCategoryServiceImpl`、`SpotProductsServiceImpl` 等【`service/Imp/`】 |
| 分页插件 | `MybatisPlusInterceptor` + `PaginationInnerInterceptor`【`configure/MybatisPlusConfig.java`】 |
| `IPage` / `Page` 分页对象 | `findAllSupplyByPage` 等 |
| `LambdaQueryWrapper` / `Wrappers.lambdaQuery` | `SupplyServiceImpl`（`eq` / `in` 条件构造） |
| 注解映射 | `@TableName`、`@TableId(type = IdType.AUTO)`、`@TableField(exist = false)` 标注非表字段的关联对象 |
| 自定义 SQL 接入 MP 分页 | 手写多表 join SQL + 首参 `IPage`，由分页插件自动拼 limit |
| 主键回填 | `@Options(useGeneratedKeys = true, keyProperty = "supplierId")` |

### 没用什么（写了就是"精通"翻车）

❌ 逻辑删除 `@TableLogic`（0 处）　❌ 乐观锁 `@Version`（0 处）
❌ 自动填充 `MetaObjectHandler` / `FieldFill`（0 处）　❌ 代码生成器
❌ 多租户 / 动态表名 / SQL 注入器　❌ `BlockAttackInnerInterceptor` 防全表更新

### 结论：能写，但按这三档写

1. **技术栈行** → 写 `MyBatis-Plus 3.5.1`（必写，无争议）
2. **技能项** → 写「**熟练**使用 MyBatis-Plus 完成单表 CRUD、分页与条件构造」——
   别写"精通"，逻辑删除/自动填充/乐观锁这三样面试官最爱问，你没用过会被问住。
3. **项目亮点** → MP 单独撑不起一条 bullet，但下面这两点**比 MP 本身更值钱**：

   - **注解式 SQL + 多表关联分页**：全项目零 XML，`@Select` 手写 distinct + 三表 join + 模糊匹配，
     靠首参 `IPage` 让 MP 分页插件接管分页，省掉手写 count 与 limit。
   - **知道什么时候不用 MP**：ES 同步那条链路刻意改用 `JdbcTemplate` 写原生多表 join SQL
     （不走 MP 的实体映射），因为要的是"跨表拼装文档字段"，实体映射反而是负担。
     → 这条能体现选型判断力，比"我会用 MP"高一个层次。

### 面试可讲的真实踩坑点

`@TableField(exist = false)` 标出来的关联对象（`tradingVariety` / `operator` 等）在写 ES 文档转换时要**手动跳过**，
否则会被当成业务字段写进索引【`es/model/EsDoc.java` 注释 + `es/core/EsDocConverter.java`】。

### 顺手提两个小瑕疵（别说，但自己心里有数）

- `SupplierMapper` 的 `@Results` 里 `score` 被映射了两次（第 18、20 行），冗余但无害。
- `int deleteById(int id)` 与 `BaseMapper#deleteById(Serializable)` 是**重载不是重写**，
  传 int 时走的是你手写的物理删除 SQL。目前没配逻辑删除所以行为一致，以后加了 `@TableLogic` 这里会不一致。

## I. RAG 技术点话术（成品，可直接粘贴）

### I-1 推荐版（标准长度）

> **RAG 私有知识库问答**：针对大模型答不了企业内部制度、流程类问题，且容易编造事实的痛点，
> 基于 **PostgreSQL + pgvector** 搭建企业私有知识库 —— 文档经 PDFBox 解析后，由自研中文分块器
> 按段落 / 句子边界切分（500 字 / 80 字重叠），调用本地 **bge-m3** 模型批量生成 1024 维向量入库，
> 并建 HNSW 余弦索引；检索能力封装为 Function Calling 工具，由大模型自主判断何时调用。
> 实测检索响应 **73~108ms**，模型可自主完成「提问 → 检索 → 带出处作答」的完整链路，
> 回答末尾标注「参考：《文档名》」；知识库无相关内容时如实说明「未检索到」而非编造答案。

### I-2 精简版（简历位置紧张时用）

> **RAG 私有知识库**：基于 PostgreSQL + pgvector + 本地 bge-m3（1024 维）搭建向量知识库，
> 自研 PDF 解析与中文分块链路，检索封装为 Function Calling 工具供大模型自主调用，
> 回答带原文出处；实测检索 73~108ms，无相关内容时如实告知不编造。

### I-3 每句话的出处（被追问时照着答）

| 简历里的话 | 项目里的实际情况 | 追问怎么答 |
|---|---|---|
| PostgreSQL + pgvector | 容器 `pgvector/pgvector:0.7.2-pg16`，库 `vec_db`，已启用 `vector` 扩展 | 复用现有 PG 体系，少一个中间件；当前数据量单机完全够用 |
| HNSW 索引 | `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops)` | 对比 IVFFlat：HNSW 不用预先训练聚类、召回更高；代价是建索引慢、吃内存 |
| 1024 维 / bge-m3 | 实测 `len(embedding) == 1024`，Ollama 本地部署 | bge-m3 中文检索效果好，且本地跑，企业文档不出内网 |
| 批量向量化 | 走 `/api/embed`（`input` 数组，batch=8），不是老的 `/api/embeddings` | 老接口一次只吃一条，200 个分块要发 200 次 HTTP |
| 中文分块 500 / 80 | `TextChunker`，段落 > 句子 > 硬切，绝对防死循环 | 硬切会把"保证金比例为合约价值的 6%"腰斩，两块都检索不到 |
| PDFBox 解析 | `setSortByPosition(true)`；识别扫描件无文字层并明确报错 | 不加 sortByPosition，双栏 PDF 会串行错乱；扫描件没文字层，必须报错而不是建一个空文档 |
| 模型自主调用 | `@Tool searchKnowledgeBase`，提示词只写"涉及制度流程先查知识库" | 是模型自己决定调用的，不是我硬编码 if-else |
| 带出处 | 回灌 chunk 原文 + 文档名，提示词要求标「参考：《文档名》」 | 引用溯源是 RAG 防幻觉的关键，用户能自己核对原文 |
| 73~108ms | 检索接口实测 `costMs` | ⚠️ 这是**检索**耗时，不含大模型推理；端到端约 75s，瓶颈在本地 7B 模型。**别把 75s 说成检索耗时** |
| 不编造 | 问「差旅费报销标准」，模型答"手册未提及" | 工具返回"未检索到"时会指示模型不得猜测 |

### I-4 两个面试官爱问的

**Q：为什么用 pgvector，不用 Milvus / Chroma？**
数据量上远没到需要专用向量库的规模（单份制度文档几十个分块）；pgvector 是 PostgreSQL 扩展，
复用现有运维体系，少引入一个中间件、少一份数据同步负担。
**若追问"数据量大了怎么办"**：Milvus / Qdrant 在千万级向量、高并发检索下优势才明显，
届时再迁移，属于架构演进，不是现在的过度设计。

**Q：检索质量怎么保证？做了 rerank 吗？**
**如实说没做 rerank** —— 这是最容易被追问穿的点，别硬说做了。
现在的做法是 topK=5 把候选一起喂给模型兜住召回；已知短板是制度类章节偏长，
最相关的那块不一定排第一。下一步计划：调小 `chunk-size` 让语义更聚焦，或引入 rerank 做二次排序。
**把"已知短板 + 下一步计划"讲出来，比假装完美更能拿分。**

### I-5 一句话总结（面试口述版）

> 我做的事本质上是**把企业内部文档变成大模型能查的资料库**。
> 大模型本身不知道我们公司的保证金加收比例、审批额度这些内部制度，直接问它就会编；
> 我把文档切块、向量化存进 pgvector，让它回答问题前先去检索真实原文，
> 再把检索结果连同出处一起交给它组织语言 —— 这样答案有据可查，查不到它也会如实说没有。

### I-6 新增两条能力的话术（2026-09-23 补齐，均已实测）

**① SSE 流式问答**

> **SSE 流式问答**：为解决本地大模型单轮推理数十秒、用户全程白屏等待的体验问题，在自研 Function
> Calling 框架上实现流式输出。由于 tools 协议必须先拿到完整 `tool_calls` 才能执行工具，采用
> 「工具阶段非流式 + 生成阶段流式」两段式编排：工具执行完毕后摘掉工具定义，以 `stream=true`
> 逐 token 推送（基于 `RestTemplate.execute` 直读响应流，`postForEntity` 会整体缓冲导致流式失效）。
> 对话运行在独立线程池，避免长耗时推理占满 Web 容器线程。实测首字延迟 7.63 秒、33 个增量块逐块到达；
> SSE 同时上报工具调用事件，前端可实时展示调用轨迹。

**② AI 合约文本解析入库**

> **AI 合约文本解析入库**：实现「向模型发送自然语言合约条款 → 模型抽取结构化字段 → 自主调用 `@Tool`
> 工具写入数据库」的闭环。由于这是项目中唯一带写操作的 AI 能力，设计了三道安全闸门：拆 preview / save
> 两步；`save` 必须携带 preview 发放的一次性令牌，服务端只从令牌缓存取字段入库，使"跳过预览直接写库"
> 在服务端不可能发生（不依赖模型遵守提示词），并保证用户确认的字段与实际入库字段严格一致；
> 入库前做品种 / 交易所 / 合约代码字典校验。令牌一次性生效，重复提交被拒。

**追问准备**

| 追问 | 答法 |
|---|---|
| 流式为什么要拆成两段？ | tools 协议要先拿到完整 tool_calls 才能执行，"边流边调"做不到；而且生成阶段如果还带着工具，模型可能再发起一轮调用，答案永远出不来。 |
| 为什么不能用 `postForEntity` 做流式？ | 它会把整个响应缓冲完才返回给调用方，逐块读取的效果就没了，必须 `execute` + ResponseExtractor 直读流。 |
| 写完库 ES 不一致怎么办？ | 双写走事务提交后的 afterCommit 回调，失败落 `es_retry_task`。实测把 ES 停掉：写入照样成功、任务入队，ES 恢复后跑一次补偿即转 SUCCESS。 |
| 为什么不让模型直接写库？ | 模型可能把"保证金 6%"抽成"60%"直接污染业务库。令牌是服务端强制的，不靠提示词约束模型自觉。 |
| 为什么 save 只有 2 个参数？ | 字段全部来自服务端令牌缓存。7B 模型在第二轮抄 14 个字段出错率不低，让它只传 token 就杜绝了抄错。 |
| 流式首字为什么还要 7 秒？ | 这 7 秒是**工具阶段**的完整推理耗时（本地 7B 模型），不是流式实现的问题。真想再快只能换更小的模型或给推理做 GPU 加速。 |

### I-7 AOP 操作日志话术（2026-09-23 补齐，`verify-operlog.sh` 14/14 通过）

#### ① 推荐版（标准长度，可直接粘贴）

> **注解驱动的操作日志**：为解决业务代码里到处手写日志、漏记且侵入主流程的问题，基于 Spring AOP 与自定义
> `@OperLog` 注解实现操作留痕 —— 业务方法只需声明模块名与动作名，由环绕通知统一采集类名方法名、请求参数、
> 客户端 IP、执行耗时与成败结果，成功记成功、抛异常记失败原因；日志经 `@Async` 独立线程池异步落库，
> 与业务线程解耦，落库异常只告警不回传，日志表写入失败时业务接口仍正常返回。已覆盖期货合约、合约条款、
> 供应商三个模块的 8 个写操作接口。

#### ② 精简版（简历位置紧张时用）

> **AOP 操作日志**：自定义 `@OperLog` 注解 + Spring AOP 环绕通知，零侵入记录模块、动作、IP、耗时与执行结果；
> 日志走独立线程池异步落库，写入失败不影响主业务；已覆盖 3 个业务模块的 8 个写操作接口。

#### ③ 一句话版（面试口述）

> 我不想在每个 Controller 方法里都写一遍"记开始时间、try、finally 记日志"，就把这段重复代码抽到了切面里；
> 方法上贴个注解说明它是哪个模块的什么操作，剩下的采集和落库全由切面统一干，写库扔给线程池，失败了也不拖累业务。

#### ④ 每句话的出处（被追问时照着答）

| 简历里的话 | 项目里的实际情况 | 追问怎么答 |
|---|---|---|
| 自定义 `@OperLog` 注解 | 只有 `module()` 和 `action()` 两个属性，加在方法上 | 注解本质是"便利贴"，告诉切面这个方法是哪个模块的什么操作；去掉它就只能按方法名前缀猜，更不准 |
| Spring AOP 环绕通知 | `@Around("@annotation(operLog)")` | 用环绕是因为耗时/成功/异常三种状态要在一个地方算完 |
| 采集 IP / 耗时 / 结果 | `X-Forwarded-For` → `X-Real-IP` → `getRemoteAddr` | 挂了 Nginx 只写 remoteAddr 会全是 127.0.0.1，审计就废了 |
| 抛异常记失败原因 | catch 后 `success=0` + `error_msg`，然后**原样 rethrow** | 吞掉异常前端会收到"成功"但数据没写进去，这是 AOP 最容易埋的雷 |
| `@Async` 独立线程池 | core2 / max4 / queue500 / CallerRuns，线程名 `oper-log-` | 和业务线程池隔离，日志表慢或挂了不会拖垮请求处理；队列满了退回业务线程同步写，宁可慢也不丢记录 |
| 落库失败不影响业务 | `saveAsync` 整段 try-catch 只打 warn | 用"把日志表改名让写入必然失败"实测过，业务接口照常返回成功 |
| 8 个写操作接口 | 期货合约 2 + 合约条款 3 + 供应商 3 | 只切写操作，查询接口不记（量太大且无审计价值） |
| 日志表 | 复用库里已有的 `sys_oper_log`（module/action/method/params/ip/cost_ms/success/error_msg） | 表本来就在，字段正好对得上，直接复用没新建 |

#### ⑤ 追问准备（这几个是必问的）

| 追问 | 答法 |
|---|---|
| **JDK 动态代理还是 CGLIB？** | **CGLIB**。Boot 2.x 起 `proxy-target-class` 默认就是 true，而且这几个 Controller 都不实现接口，JDK 代理根本没接口可代。运行时代理类名实测是 `FuturesContractTextController$$EnhancerBySpringCGLIB$$180d02ab`，我写了单测钉死这一点。 |
| 依赖里有 aspectjweaver，是 AspectJ 静态织入吗？ | 不是。aspectjweaver 只负责解析 `@Aspect` 和切点表达式，真正织入是运行时用 CGLIB 生成子类。要上 AspectJ 织入得开 LTW 或编译期织入，本项目都没开。 |
| 依赖树里怎么没有 cglib 的 jar？ | Spring 5 已经把 CGLIB 重打包进 `spring-core`（`org.springframework.cglib`），不需要单独引。**不要说"引入了第三方 CGLIB"，那是错的。** |
| 为什么用 @Around，不用 @Before + @After 拼？ | 开始时间存哪儿的问题。分开写只能存成成员变量，切面是单例，并发时 A 请求的开始时间会被 B 请求覆盖，耗时全乱。环绕通知用方法内局部变量，天生不串。 |
| 切面吞掉异常会怎样？ | 前端收到"操作成功"但实际失败了，是最坑的线上问题。所以 catch 只为了记录，最后一定 `throw e` 原样抛回去。 |
| CGLIB 有什么限制？ | final 类、final 方法、private 方法代理不了，加了注解会**静默失效**（不报错但没日志）。所以被切的方法不能写成 final/private。 |
| 敏感字段（密码）会不会被记进去？ | 会记参数 JSON，所以涉及敏感信息的方法我不加注解；另外参数超过 2000 字符会截断，request/response/文件流对象自动跳过。 |
| 异步还有什么坑？ | `@Async` 方法必须走 Spring 代理才生效，同类里 `this.xxx()` 调用会退化成同步；另外返回值只能是 void 或 Future，返回 boolean 调用方拿到的是 null。 |

#### ⑥ 千万别写（这条的边界）

❌ "引入第三方 CGLIB" —— Spring 已内置，说了反而错
❌ "操作人/用户体系" —— 本项目没做登录，`username` 字段目前固定 `anonymous`（接鉴权后从 request 取）
❌ "日志表是我建的" —— `sys_oper_log` 库里本来就有，是复用的
❌ "日志检索/可视化页面" —— 没有，只落库
❌ "记录响应结果" —— 没记，只记入参
